# Placement Decision Flow

「新しい処理をどこに置くか」を、オーケストレーター／サブエージェント定義／スキルの3層から
決定的に判定します。

## 起動条件（明示指名のみ）

このスキルは、利用者または上位のエージェントから**明示的に指名されたときだけ**起動します
（FR-018 / FR-019）。

- 起動の例: 「この処理をどこに置くべきか判断して」「配置を相談したい」
- 文脈から判断が必要そうに見えても、**指名なしに自動起動してはなりません**。他の作業の
  途中で判断が割り込むと、「判断で止まる時間を減らす」という目的に逆行します
- 指名がない限り、依頼された作業をそのまま続けます

## 実行手順

### 1. 対象を 1 件に定める

相談された処理が複数ある場合は、**1 件ずつ**判定します。複数をまとめて 1 つの配置先に
丸めてはなりません。性質の異なる処理を同じ場所に寄せることが、このスキルが防ごうと
している誤配置そのものだからです。

### 2. 自然文から 4 分岐の回答を抽出する（FR-013）

| 分岐 | 質問 | 取りうる値 |
|---|---|---|
| `governance` | 実行前検証・権限・外部接続を伴うか | `yes` / `no` / `unknown` |
| `orchestration` | タスクの分解・委任・統合か | `yes` / `no` / `unknown` |
| `reusable` | 他のサブエージェントでも使いそうか | `yes` / `no` / `unknown` |
| `needs_code` | 決定論的な実行コードが必要か | `yes` / `no` / `unknown` |

判断がつかない分岐は `unknown` とします。**推測で `yes` / `no` を埋めてはなりません**
（FR-006）。回答が `unknown` のままでも、先行するゲートで確定すれば判断は返せます。

### 3. AI としての結論を先に出す

抽出した回答から、自分自身の結論（配置先）を先に決めます。これは手順 5 でコードの結論と
比較するために必要です。コードの出力を先に見てしまうと、検証が常に成功して意味を失います。

### 4. 判定コードで機械的に検証する（FR-014）

同じ回答で `scripts/decide.sh` を実行し、コードの結論を得ます。

```bash
scripts/decide.sh --governance <yes|no|unknown> --orchestration <yes|no|unknown> \
  --reusable <yes|no|unknown> --needs-code <yes|no|unknown>
```

出力は `key=value` 形式です。

- `result=decision` — 配置先が確定した。`target` / `reason` / `branches` が返る
- `result=ask` — 判断に必要な回答が足りない。`missing` の分岐を利用者に問い返す
  （FR-006 / FR-012）
- 終了コード 2 — 値の指定が不正。値を正して再実行する

### 5. 食い違ったら矛盾として提示する（FR-015）

手順 3 の AI の結論と手順 4 のコードの結論が異なる場合は、**黙って一方を採用しません**。
両方の結論を並べ、**矛盾していること**を明示して提示します。採用する基準は**コード側**です。

### 6. 再利用候補を調べる（FR-009）

配置先がスキル（`skill-instructions` / `skill-scripts`）のときは、既存スキルを探索し、
重なるものがあれば新規作成ではなく再利用を提案します。

```bash
scripts/find-skills.sh --query <処理を表す語>
```

**候補が出力された場合のみ**再利用を提案します。候補が 0 件のときは「重なる既存スキルは
ない」と伝え、新規作成を妨げません。

## ガバナンス項目の扱い

実行前検証・権限・外部接続のいずれかを伴う処理（`governance=yes`）は、**`reusable` と
`needs_code` の答えにかかわらず**サブエージェント定義側に確定します。

対象になる処理:

| 分類 | 具体例 |
|---|---|
| 実行前検証 | 実行前に秘密情報が含まれていないか検査する |
| 権限 | ツール実行やファイル変更の許可を扱う |
| 外部接続 | 外部 API の呼び出しや認証を伴う |

- 「他のサブエージェントでも使うからスキルにすべき」と判断しては**なりません**
  （FR-022）。判断表 1 行目の `reusable` が `*` なのはこの規則です
- 理由は**発火の保証**です。サブエージェント定義は起動条件・ツール・権限を構造として
  持つため必ず通りますが、スキルは呼び出し側の裁量で発火するため、発火しない経路が
  残ります。実行前検証や権限確認を「たまたま実行された」に依存させてはなりません
- 判定は `decide.sh` の `reason=governance` として現れ、`branches` は `governance=yes`
  だけで止まります

### 手順とガバナンスの両方を持つ処理

1 つの処理が「使い回せる手順」と「検証・権限・接続」を併せ持つ場合は、**1 つの配置先に
丸めず、分割案を示します**。

1. 全体を `decide.sh` にかけます。`target=subagent-definition` / `reason=governance` が
   返り、これはガバナンス部分の配置先です
2. ガバナンスを取り除いた**手順部分**を、`governance=no` でもう一度 `decide.sh` に
   かけます（`--orchestration` / `--reusable` / `--needs-code` は手順部分の性質で答える）。
   ここで `skill-instructions` / `skill-scripts` が返れば、手順はスキルに置けます
3. 「手順はスキル、検証・権限・接続はサブエージェント定義」という分割案を提示し、定義側
   からスキルを呼び出す構造を示します

分割案はコードの結論を上書きしません。**2 つの判定（全体と手順部分）をそれぞれ提示**
します。

### `governance` が不明なとき

`governance` が `unknown` のときは、他の 3 分岐が確定していても `result=ask` /
`missing=governance` が返ります。**推測で `yes` / `no` を埋めず**、利用者に問い返します
（FR-006 / FR-012）。

## 提示フォーマット

`decide.sh` の `key=value` をそのまま見せるのではなく、**日本語の文章**として提示します。
最低限、次の 3 点を含めます。

1. **結論** — 配置先（`target`）
2. **適用した分岐と理由** — どの質問に何と答えたか（`branches`）と、その分岐が何を根拠に
   配置先を決めたか（`reason`）
3. **次に何をどこに書くか** — 対象リポジトリ配下の**相対パス**

### 配置先の意味

| `target` | 配置先 | 成果物 |
|---|---|---|
| `orchestrator` | オーケストレーター | 分解・委任・統合の責務 |
| `subagent-definition` | サブエージェント定義 | エージェント定義（起動条件・利用可能なツール・権限を含む） |
| `skill-instructions` | スキルの手順 | `SKILL.md` |
| `skill-scripts` | スキルの実行コード | `scripts/` 配下のスクリプト |

配置先がスキルのときは、**手順は `SKILL.md`、実行コードは `scripts/`** という区別を必ず
示します（FR-003）。2 つは同じスキルに同居できますが、置くものが違います。

### 具体的なパスは慣習の検出結果に従う

パスを決め打ちせず、`--detect-conventions` の結果に沿って**リポジトリ相対パス**を示します。

```bash
scripts/find-skills.sh --detect-conventions
```

出力は `layer<TAB>path<TAB>exists` の 4 行です。

- `exists=yes` の慣習があれば、そのパスをそのまま示します
- 対象の `layer` の慣習がすべて `exists=no` のときは、役割の名前（例: 「サブエージェント
  定義」）と**目安のパス**を併記し、利用者が選べるようにします

**リポジトリ外のパスを示してはなりません**（FR-020）。示すパスは必ず対象リポジトリ配下の
相対パスです。

### 問い返しのとき

`result=ask` のときは、`missing` の分岐を日本語の質問として **1 つだけ**尋ねます。複数の
質問を並べず、評価順で最初の不明だけを尋ねます。**判断を保留したまま終わらせてはなりません**
（FR-012）。

## 判断基準

判断基準の正は `references/criteria.md` です。評価順序は
`governance` → `orchestration` → `reusable` → `needs_code` で固定されており、
`governance=yes` のときは `reusable` を評価せず `subagent-definition` に確定します。
