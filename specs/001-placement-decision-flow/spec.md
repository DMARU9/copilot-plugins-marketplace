# Feature Specification: スキルとエージェントの配置判断フロー

**Feature Branch**: `001-placement-decision-flow`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "スキルとエージェントでどちらで作成すればよいかを判断するフローをサブエージェントまたはスキルで作成し、プラグインとして新規に作成したい"

## 背景と課題

オーケストレーター・サブエージェント・スキルの3層でエージェントを組み立てていると、
新しい処理を書き始めるたびに「これはどこに置くのか」で手が止まる。判断を誤ると、
同じスクリプトが複数のサブエージェント配下に重複して置かれ、修正が散らばる。

判断の基準は既に言語化されている（再利用の広がり、実行コードの有無、ガバナンス該当性の3点）。
しかし基準が文書や人の記憶にあるだけでは、作業のたびに引き出されず、判断が揺れる。
本機能は、この判断基準を**誰でも同じ結果になる形で呼び出せる**ようにする。

## Clarifications

### Session 2026-09-12

- Q: 「同じ入力なら同じ判断を返す」（FR-008 / SC-006）をどう担保するか → A: AI 判断＋機械検証の併用。自由記述の相談から AI が判断し、その結果を検証する判定コードを同梱して矛盾を検出する
- Q: 既存配置の再利用（FR-009）をどう実現するか → A: リポジトリ内の `SKILL.md` を探索し、名前と説明を突き合わせて再利用候補を提示する（特定ディレクトリに依存しない）
- Q: この判断フローをいつ起動するか → A: 明示指名のみで起動。上位のエージェント（最上位）から指名されたときだけ動き、文脈による自動提案はしない
- Q: 判断フローをスキルとエージェントのどちらで作り、プラグインに何を同梱するか → A: スキルのみ。プラグインは判断フローのスキルを配布し、上位エージェントは利用側のプロジェクトが用意する（本機能の対象外）
- Q: 「どのファイルに何を書くか」をどこまで具体化するか → A: 配置先はすべて対象リポジトリ配下に限る。役割ベースの判断に加え、対象リポジトリ内の慣習に沿った相対パスで示す
- Q: 判断分岐の評価順序 → A: ガバナンス該当性を最初のゲートに置く。該当すれば即サブエージェント定義とし、該当しない場合に記事の3分岐（分解・委任・統合 → 他のサブエージェントでも使うか → 実行コードが必要か）を評価する

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新しい処理の置き場所を一度の相談で決める (Priority: P1)

エージェント構成を組み立てている開発者として、新しい処理・手順・スクリプトを書き始める前に
「これはどこに置くか」を相談し、配置先とその理由を得たい。そうすれば、判断で止まる時間が
なくなり、後から重複配置に気づいて直す手戻りも起きない。

**Why this priority**: 本機能の中心価値。ここが機能しないと、同じスクリプトを3箇所に複製し
修正が3箇所に散るという元の失敗が再発する。

**Independent Test**: 代表的な4種類の処理をそれぞれ提示し、期待する配置先が返ることを
個別に確認できる。（分解・委任・統合の呼び出し／1つのサブエージェント内で完結する手順／
複数のサブエージェントで使い回す手順／汎用的な決定論的コード）

**Acceptance Scenarios**:

1. **Given** タスクの分解・委任・統合に必要な呼び出しを追加しようとしている、**When** 配置を相談する、**Then** 配置先は「オーケストレーター」となり、処理そのものを書かない原則が併記される
2. **Given** 1つのサブエージェントでしか使わず、実行コードも伴わない進め方の指示、**When** 相談する、**Then** 配置先は「そのサブエージェントの定義」となる
3. **Given** 複数のサブエージェントから同じ手順を使いたい、**When** 相談する、**Then** 配置先は「スキルの手順（SKILL.md）」となり、使い回される点が理由として示される
4. **Given** 専門によらず汎用的で、同じ入力に同じ結果を返すべき処理コード、**When** 相談する、**Then** 配置先は「スキルの実行コード（scripts）」となり、決定論的な処理である点が理由として示される
5. **Given** 判断に必要な情報（その処理を使う予定のサブエージェントなど）がまだ決まっていない、**When** 相談する、**Then** 推測で配置先を断定せず、判断に必要な点が問い返される
6. **Given** 追加しようとしている処理と同じものが既存のスキルに存在する、**When** 相談する、**Then** 新規に作らず既存の再利用が提案され、該当するスキルが示される
7. **Given** 既存スキルが `plugins/` 以外（プロジェクト固有のスキル置き場など）に置かれている、**When** 相談する、**Then** 置き場所によらず再利用候補として提示される
8. **Given** 判断の指名をせずに他の作業（コードの追加など）を進めている、**When** その作業を続ける、**Then** 判断フローは自動起動せず、作業が中断されない（指名したときのみ起動する）

---

### User Story 2 - ガバナンス項目をスキルに紛れ込ませない (Priority: P2)

エージェント構成を組み立てている開発者として、実行前検証・権限・外部接続を追加するときは、
「使い回せるか」だけで判断せず、必ず機械的に発火する場所へ置きたい。そうすれば、
スキル側に置いて発火しないという安全上の穴を作らずに済む。

**Why this priority**: 判断フローの自然な流れ（使い回せるならスキル）に従うと、ガバナンス項目まで
スキルへ寄ってしまう。これは安全性の前提を壊すため、P1 の判断ができても防げない。

**Independent Test**: ガバナンスに属する3項目（実行前検証・権限・外部接続）を提示し、
いずれも「スキル」ではなくサブエージェント定義側だと返ることを確認できる。

**Acceptance Scenarios**:

1. **Given** 実行前に必ず走らせたい検証を追加しようとしている、**When** 相談する、**Then** 配置先は「サブエージェント定義（実行前検証）」となり、呼び出しのたびに読まれる保証がないためスキルには置けないという理由が示される
2. **Given** あるサブエージェントに使わせる tool を制限したい、**When** 相談する、**Then** 配置先は「サブエージェント定義（権限）」となる
3. **Given** 外部ツールへの接続設定を追加しようとしている、**When** 相談する、**Then** 配置先は「呼ぶ側のサブエージェント定義（接続設定）」となる
4. **Given** すべてのサブエージェントで使い回したい実行前検証を追加しようとしている、**When** 相談する、**Then** 「他でも使う」に該当してもスキルではなくサブエージェント定義と判断され、ガバナンスを優先した理由が示される

---

### User Story 3 - 判断の根拠と次の一歩を得る (Priority: P3)

エージェント構成を組み立てている開発者として、判断結果だけでなく、どの基準でそう決まったかと、
配置先で具体的に何を書けばよいかまで知りたい。そうすれば、判断に納得できないときも自分で
確かめられ、決まった後の最初の一歩で再び止まらない。

**Why this priority**: P1/P2 が返す答えの信頼性と実用性を支える。無くても配置先は分かるため
優先度は下がるが、これが無いと自己流の判断に戻りやすい。

**Independent Test**: 任意の処理を提示し、適用された分岐（質問と回答の並び）と、配置先での
置き方の区別（手順か実行コードか）が示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** ある処理について判断結果が返ってきた、**When** 結果を読む、**Then** どの分岐をどの順で通ったかが示される
2. **Given** 配置先がスキルと判断された、**When** 結果を読む、**Then** 手順は SKILL.md、実行コードは scripts という置き方の区別が示される

---

### Edge Cases

- **判断に必要な情報が足りない場合**（例: その処理を使う予定のサブエージェントが未定）:
  推測で断定せず、判断に必要な点を問い返す。
- **複数の性質を併せ持つ処理**（例: 手順と実行コードの両方、かつガバナンスにも該当）:
  分割して配置する案を示す（手順はスキル、検証はサブエージェント定義）。
- **ガバナンスにも該当し、かつ複数のサブエージェントで使い回せる処理**（例: 全員に掛けたい
  実行前検証）: 再利用できることを理由にスキルへ流さず、ガバナンスを優先してサブエージェント
  定義と判断する。併せて、共通化したい部分があればスキルと定義の分担を分割案として示す。
- **同じ処理が既存のスキルにある場合**: 新規作成ではなく既存の再利用を提案する。
- **サブエージェントが1つしかない構成**で「他でも使うか」が判断できない場合:
  現時点の利用範囲で判断し、その前提を明示する。
- **オーケストレーターから直接呼びたい汎用処理**: オーケストレーターには置かず、
  スキルとして提供する案を示す。
- **判断が既存の配置と矛盾する場合**: 矛盾する既存の置き場所を指摘し、移すかどうかは
  利用者が決められるようにする。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 利用者は、追加しようとしている処理の内容を伝えることで、配置先の判断を得られなければならない
- **FR-002**: 判断の選択肢は「オーケストレーター」「サブエージェント定義」「スキル」の3層でなければならない
- **FR-003**: 配置先がスキルと判断された場合、手順（SKILL.md）と実行コード（scripts）のどちらに置くかを区別して示さなければならない
- **FR-004**: 判断結果には、適用した分岐と配置先の理由を含めなければならない
- **FR-005**: ガバナンスに属する項目（実行前検証・権限・外部接続）は、スキルではなくサブエージェント定義側と判断しなければならない
- **FR-006**: 判断に必要な情報が不足している場合、推測で断定せず利用者に問い返さなければならない
- **FR-007**: 判断結果は、どのファイルに何を書くかが分かる具体性で、対象リポジトリ配下の相対パスとして示さなければならない
- **FR-008**: 同じ入力に対しては同じ判断を返さなければならない（判断が気分や担当者で変わってはならない）
- **FR-009**: 判断にあたり、リポジトリ内の `SKILL.md` を探索し、追加しようとしている処理と重なる既存スキルがある場合はそれを再利用候補として提示しなければならない
- **FR-010**: 既存スキルの探索は、特定のディレクトリ構成に依存してはならない（`plugins/` 配下、`.github/skills/` 配下などを同様に扱う）
- **FR-011**: 判断基準は、主要な公式設計（Anthropic / OpenAI / Microsoft / Google / LangGraph）の指針と矛盾してはならない
- **FR-012**: いずれの入力に対しても、判断を保留したまま終わってはならない（判断または問い返しのいずれかを必ず返す）
- **FR-013**: 利用者が自然文で伝えた処理内容から、AI が配置先の判断を行わなければならない
- **FR-014**: AI が出した判断は、同梱された判定コードで機械的に検証されなければならない
- **FR-015**: 判定コードが AI の判断と矛盾する配置先を導いた場合、その矛盾を利用者に提示しなければならない（黙って一方を採用してはならない）
- **FR-016**: 判定コードは、構造化入力（各分岐の回答）を受け取り、配置先と適用した分岐を機械可読な形式で返さなければならない
- **FR-017**: 判断基準を変更する場合、手順記述と判定コードの両方を同期して変更しなければならない（片方のみの変更を認めない）
- **FR-018**: 本判断フローは、利用者または上位のエージェントからの明示的な指名によってのみ起動しなければならない
- **FR-019**: 判断が必要そうな文脈を検出しても、指名なしに自動起動してはならない（起動は常に明示の指名による）
- **FR-020**: 判断結果が示す配置先は、対象リポジトリ配下のパスに限らなければならない（リポジトリ外やユーザー環境の設定ディレクトリを配置先として提示してはならない）
- **FR-021**: 判断は、次の順序で評価しなければならない。（1）ガバナンス該当性 →（2）タスクの分解・委任・統合か →（3）他のサブエージェントでも使うか →（4）実行コードが必要か
- **FR-022**: ガバナンスに該当する処理は、後続の「他のサブエージェントでも使うか」の結果にかかわらず、サブエージェント定義と判断しなければならない（再利用可能であることを理由にスキルへ差し替えてはならない）

### Key Entities

- **配置対象（処理）**: 追加しようとしている手順・コード。属性は「使い回す範囲」「実行コードの有無」
  「ガバナンス該当性」。
- **配置先**: オーケストレーター / サブエージェント定義 / スキル（手順・実行コード）。
- **判断分岐**: 次の順序で評価する質問と、その結果。（1）ガバナンスに該当するか（該当すれば
  以降を評価せずサブエージェント定義に確定） →（2）タスクの分解・委任・統合か →（3）他の
  サブエージェントでも使うか →（4）実行コードが必要か。この順序は固定され、同じ入力に対して
  常に同じ配置先を導く。
- **ガバナンス項目**: 実行前検証・権限・外部接続。
- **判定コード**: 各分岐の回答を入力として受け取り、配置先と適用した分岐を返す決定論的な処理。
  AI の判断を検証する役割を持ち、判断基準の変更時は手順記述と同期して更新する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 代表的な4種類の処理すべてで、判断が1回の相談で確定する（4/4）
- **SC-002**: ガバナンス項目を「スキル」と誤って判断する件数が 0 件
- **SC-003**: 同じ処理が2つ以上のサブエージェント配下に重複して配置される件数が 0 件
- **SC-004**: 「どこに置くか」で停止する時間が1件あたり5分未満になる
- **SC-005**: 判断結果が提示されたすべてのケースで、適用された分岐が示される（利用者が自分で根拠を確かめられる）
- **SC-006**: 同じ入力に対して、別のセッション・別のプロジェクトでも同じ判断が返る
- **SC-007**: 判断に必要な情報が足りないケースで、推測による断定が 0 件（問い返しが返る）
- **SC-008**: AI の判断と判定コードの結果が食い違ったケースで、矛盾が提示される（黙殺 0 件）
- **SC-009**: 指名なしに起動する件数が 0 件（不要な場面で作業を中断させない）
- **SC-010**: 配置先が複数に解釈し得る処理（ガバナンスに該当し、かつ使い回せるもの）でも、常に同じ配置先が導かれる（評価順序の入れ替わりによるぶれが 0 件）

## Assumptions

- 配置先は**対象リポジトリ配下に限る**。リポジトリ外（ユーザー環境の設定ディレクトリ、
  マシン全体の共有設定など）は配置先として示さない。作業の対象となるリポジトリが明確な場面で
  使うスキルであり、その外へファイルを作る想定をしないため。具体パスは対象リポジトリ内の
  慣習（既存のスキル置き場、エージェント定義の置き場）から推定し、推定できない場合は
  役割と併せて目安のパスを示す。
- 利用者は、オーケストレーター／サブエージェント／スキルという3層の構成でエージェントを
  組み立てている。
- 起動のきっかけは**明示的な指名のみ**とする。判断が必要そうな文脈を検出しての自動提案は
  行わない。上位のエージェント（最上位）から指名されたときだけ起動する。判断の起動条件が
  広いと、作業の途中で判断が割り込むことになり、「判断で止まる時間を減らす」という目的と
  逆行するため。
- 判断の対象は「これから追加する処理」であり、**既存の配置全体を監査して違反を検出する機能は
  対象外**とする。
- **判断の提示までとし、ファイルの作成・変更を自動で行うことは対象外**とする
  （配置先を示すが、配置そのものは利用者の作業とする）。
- 既存スキルの探索は、作業中のリポジトリ内を**読み取りのみ**で行う。ファイルの変更や、
  ネットワーク越しのマーケットプレイス探索は対象外とする。探索時に既存スキルの中身を読む
  ことは許容するが、参照に留め、内容の転記は行わない。
- 判断基準の正は、次の4分類とする。決定論的で専門によらず汎用的な処理コード → スキルの
  実行コード。実務知としての手順 → スキルの手順。ガバナンス（実行前検証・権限・外部接続）→
  サブエージェント定義。タスクの分解と委任 → オーケストレーター。
- 判断の判定方式は、**AI 判断＋機械検証の併用**とする。利用者は自然文で相談できる（判断の
  ハードルを上げない）。同時に、判断基準を判定コードとして同梱し、AI の判断と矛盾があれば
  それを提示する。これにより FR-008 / SC-006（同じ入力で同じ判断）を実測で裏付けられる。
  両者を分ける理由は、自然文入力の解釈は AI の得意領域、基準の適用は決定論的な処理の得意
  領域であり、片方だけでは「相談しやすさ」と「判断の再現性」を両立できないため。
- 矛盾が生じた場合に**どちらを正とするかは、判定コード側の基準を正**とする。手順記述の解釈
  揺れではなく、明文化された基準からの逸脱を検出するのが機械検証の目的であるため。
- 成果物の形態は**スキル**とし、プラグインには**スキルのみを同梱**する。上位エージェントは
  利用側のプロジェクトが用意するものとし、本機能の対象外とする。理由は3点。(1) 判断フローは
  「複数のサブエージェントから使い回したい手順」であり、判断基準そのものがスキルを指す。
  (2) Agent Plugins 1.0.0 の移植可能な部品はスキルと MCP サーバーの2種類のみで、エージェントは
  「クライアント固有すぎて安定した契約にできない」として範囲外とされている。プラグインに
  エージェントを同梱しても、適合クライアントはそれを発見できない。
  (3) 判断基準の正である配置サマリーでも「手順」はスキル側に分類されている。
- 配布形態は本リポジトリへの**新規プラグイン追加**とし、既存プラグインの変更は対象外とする。
- 記事で参照した外部の公式ドキュメントは判断基準の根拠として引用するが、その内容の追随
  （最新版への更新）は本機能の対象外とする。
- プラグインとしての体裁は、本リポジトリの憲章（プラグインの自己完結、マニフェストと起動
  トリガーの契約、副作用前の検証、バージョン管理）に従う。
