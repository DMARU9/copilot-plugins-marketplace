# Phase 0 Research: スキルとエージェントの配置判断フロー

**Feature**: `001-placement-decision-flow` | **Date**: 2026-09-12

`spec.md` の Clarifications で確定しなかった論点（checklists/requirements.md の Deferred）と、
Technical Context の技術選択を解決する。

---

## R-1. 既存スキルの「重なる」判定基準（D-1）

**Decision**: 名前と説明の**字句一致**で候補を列挙し、意味的な「重なり」の判断は AI に委ねる。
`find-skills.sh` は `--query` のトークンが `name` または `description` に部分一致する
`SKILL.md` を候補として返す。AI は**返された候補の中からのみ**再利用を提案できる。

**Rationale**: 2 つの要件を同時に満たす必要がある。FR-009 は重なりを検出せよと言い、FR-008 /
SC-006 は同じ入力に同じ判断を返せと言う。意味的類似の判定をコードに持たせると決定性が崩れ、
AI に任せると再現性が崩れる。**字句一致は決定的**、**意味判断は AI の得意領域**という分担に
すれば、両方を満たせる。候補を限定することで、AI の判断ぶれも候補集合の範囲に収まる。

**Alternatives considered**:
- 名前の完全一致のみ: 再現性は最高だが再現率が低い。`code-review` と `review-code` のような
  表記ゆれを取り逃し、FR-009 の意図（重複配置の防止）を満たせない
- 説明文の編集距離・類似度スコア: 閾値の根拠が説明できず、リポジトリの状態で閾値調整が必要に
  なる。決定性は保てるが「なぜ候補なのか」を利用者に説明できない
- AI に全 `SKILL.md` を読ませて類似判断: コンテキスト消費が大きく、判断が実行ごとに揺れる

## R-2. 判定コードの入力スキーマと「不明」の扱い（D-2）

**Decision**: 入力は 4 つのフィールド（`governance` / `orchestration` / `reusable` /
`needs_code`）で、各値は `yes` / `no` / `unknown` の **3 値**。引数を省略した場合は
`unknown` と同義。**評価順序に従って必要な回答から順に評価し、`unknown` に到達した時点で
`result=ask` と `missing=<質問名>` を返す**。

**Rationale**: FR-006（不足時は問い返す）と FR-012（判断か問い返しのいずれかを必ず返す）を、
短絡評価で自然に実現できる。評価順序（R-5）と一貫するため、「後続の質問が未回答でも、先行する
ゲートで確定するなら判断を返す」という正しい振る舞いになる。3 値にすることで
「まだ決めていない」と「いいえ」を区別できる。

**Alternatives considered**:
- 2 値（`yes` / `no`）のみ: 未回答を表現できず、FR-006 の問い返しが実装できない
- 全 4 値を必須にしてから判定: ガバナンスで確定する場合に無関係な質問への回答を強要し、
  SC-004a（1 往復で確定）を満たせない
- `unknown` を独立した第 5 の配置先として返す: FR-002 は配置先を 3 層に限定しており、矛盾する

## R-3. AI 判断と判定コードの実行順序（D-3）

**Decision**: **AI が先に判断し、判定コードが検証する**。具体的には次の流れ。

1. AI が自然文から 4 フィールドの回答を抽出する（FR-013 の判断）
2. AI がその回答から**自分自身の結論**（配置先）を出す
3. AI が同じ回答で `decide.sh` を実行し、**コードの結論**を得る
4. 2 と 3 が食い違えば矛盾として提示する（FR-015）。基準の正はコード側（spec の Assumptions）

**Rationale**: FR-013 → FR-014 の順序が仕様に明記されており、これに素直に従う。AI の結論と
コードの結論を**別々に**出させることで初めて「矛盾の検出」が意味を持つ。もし AI がコードの
出力をそのまま報告するだけなら、検証は常に成功し FR-014 が空虚になる。

**Alternatives considered**:
- コードを先に実行し AI が補足: 矛盾が検出できない。AI は常にコードの結論を追認するだけになる
- AI の判断を採用せずコードのみ: FR-013（自然文からの判断）を満たさない。利用者は構造化入力を
  自分で用意しなければならなくなる
- AI の結論を正とする: spec の Assumptions が「コード側の基準を正とする」と定めているため不可

---

## R-4. 判断結果の提示フォーマット（D-4）

**Decision**: 二層にする。`decide.sh` の標準出力は **`key=value` 形式の ASCII 行**（機械可読・
FR-016）。AI はそれを**日本語の文章**で提示し、適用した分岐（どの質問に何と答えたか）と
配置先の理由を含める（FR-004 / SC-005）。

**Rationale**: FR-016 が機械可読性を要求し、FR-004 / SC-005 が人間向けの根拠提示を要求する。
`key=value` は JSON パーサを必要とせず、bash 3.2 でも扱える（憲章 VII）。値は ASCII の
識別子に固定するので、ロケール依存の出力崩れも起きない。

**Alternatives considered**:
- JSON 出力: パースに `jq` が必要で、追加依存を持ち込む（憲章 VII に反する）
- 表形式（人間向け）のみ: FR-016 の機械可読性を満たさない。テストで固定しづらい
- コードが日本語の文章を返す: 出力がロケール依存になり、テストの期待値も壊れやすい

## R-5. 複数処理をまとめて相談した場合の扱い（D-5）

**Decision**: **1 回の実行につき 1 処理**。複数の処理が提示された場合は、AI が 1 件ずつ
`decide.sh` を実行し、**処理ごとに独立した判断結果**を返す。まとめて 1 つの配置先に丸めない。

**Rationale**: FR-001 は単数の処理を想定しており、「まとめて相談されたから同じ場所」という
判断は、まさに本機能が防ごうとしている誤配置（性質の異なる処理を同じ場所に寄せる）を生む。
処理ごとに分ければ、R-2 の問い返しも処理単位で正確に行える。

**Alternatives considered**:
- 複数を 1 つの配置先に集約: 異なる性質の処理が混ざり、SC-003（重複配置 0 件）の測定が濁る
- 複数対応のため入力を配列にする: bash 3.2 で配列入力を扱うのが煩雑になり、CLI 契約が
  過剰に複雑化する。1 件ずつ呼べば同じ結果が得られる

## R-6. 配置先の具体パスの決定方法（D-6 / FR-007 / FR-020）

**Decision**: **慣習の検出 + 目安の提示**の二段構え。
`find-skills.sh --detect-conventions` が対象リポジトリの慣習ディレクトリを **4 件すべて**
報告する（実在しないものも `exists=no` として報告する）。AI は検出結果に応じて具体パスを示し、
検出できなければ役割名と目安のパスを併記する。

検出対象（常に 4 行を出力する）:

| `layer` | 慣習ディレクトリの候補 |
|---|---|
| `skill` | `.github/skills/`、`plugins/*/skills/` |
| `subagent` | `.github/agents/`、`.claude/agents/` |

**オーケストレーターは `subagent` として報告する**（オーケストレーターもエージェント定義の
一種であり、クライアント上で置き場所が分かれる設計を採らないため）。`layer` の列挙を
`skill` / `subagent` の 2 値に保つのは、判定を単純にし、`exists` の解釈をコード側に持ち込まない
ため。

**実在しないものも報告する理由**: `exists=no` は「その慣習が使われていない」という情報であり、
AI が目安のパスを示すかどうかの判断材料になる。行数が固定されるため、テストも「4 行である
こと」で書式を固定できる（テストが実リポジトリの構成に依存しなくなる）。

**Rationale**: パスを決め打ちすると、このプラグインを別のリポジトリで使ったときに誤ったパスを
示す（FR-010 と同じ問題意識）。かといって常に利用者へ質問すると SC-004a（1 往復で確定）を
満たせない。**存在確認は決定的**なので、検出はコードで行い、解釈は AI が行う。

**Alternatives considered**:
- 特定パスに固定: FR-010 の趣旨に反する。別リポジトリで誤案内になる
- 毎回利用者に尋ねる: SC-004a を満たせない
- パスを示さず役割のみ: FR-007（どのファイルに何を書くか分かる具体性）を満たせない

## R-7. 既存スキル探索の深さと除外（D-7）

**Decision**: `git rev-parse --show-toplevel` で**リポジトリルート**を求め、そこから
`find` で `SKILL.md` を探索する。以下のディレクトリは `-prune` で除外する。

`.git`、`node_modules`、`tmp`、`dist`、`build`、`vendor`、`.venv`、`venv`、`__pycache__`

git リポジトリでない場合はカレントディレクトリをルートとする。`--exclude <名前>` で
追加の除外を指定できる。ドット始まりのディレクトリは**除外しない**（`.github/skills/` が
FR-010 の明示的な対象のため）。

**Rationale**: 除外しないと `.git` 内のオブジェクトや `node_modules` の大量ファイルを走査し、
Performance Goals（1 万ファイルで 2 秒未満）を満たせない。`.github/` を除外すると FR-010 /
受入シナリオ 7 が壊れるため、ドット始まりを一律に除外してはならない。

**Alternatives considered**:
- `git ls-files` を使う: `.gitignore` を尊重できるが、**未追跡の新規スキルを検出できない**。
  まさに「これから作るスキル」を探す用途なので不適
- 除外なしの全走査: 大規模リポジトリで性能要件を満たせない
- 深さ制限（`-maxdepth`）: スキルの標準的な深さは 3〜4 階層（`plugins/<p>/skills/<s>/SKILL.md`）
  で、制限値の根拠が薄弱。除外のほうが意図が明確

## R-8. 判定コードの実装言語と bash 互換性（D-9）

**Decision**: **bash で実装し、`declare -A`（連想配列）を使わない**。分岐は `case` 文で表現する。

**Rationale**: 憲章 VII は依存を標準的なシェル環境に留めることを要求する。実測の結果、
このリポジトリの既存スクリプト（`validate-issue.sh` / `create-issue.sh`）は `declare -A` を
使っており bash 4+ を要求していた。しかし **macOS が同梱する bash は 3.2** であり、
`declare -A` は動作しない。判断ロジックは 5 分岐しかないため、`case` 文で十分に表現できる。
連想配列を避けることで、依存を増やさずに対応環境を広げられる。

**実測記録**（2026-09-12）:
```text
$ echo "bash: $BASH_VERSION"
bash: 5.2.21(1)-release
$ grep -l "declare -A" plugins/*/skills/*/scripts/*.sh
plugins/github-issue/skills/github-issue/scripts/create-issue.sh
plugins/github-issue/skills/github-issue/scripts/validate-issue.sh
```

**Alternatives considered**:
- Python: JSON の扱いが楽だが、追加の実行時依存になる（憲章 VII）。判断ロジックに対して過剰
- `declare -A` を使う: bash 4+ を要求し、macOS 標準環境で動かない。既存スクリプトと同じ制約を
  新規に持ち込む理由がない
- POSIX sh に限定: `[[ ]]` や `local` が使えず可読性が落ちる。bash 3.2 で十分広い

## R-9. 判断表と判定コードの同期の強制方法（FR-017）

**Decision**: `references/criteria.md` に**固定書式の判断表**を置き、
`tests/test_criteria_sync.sh` がその表を**テストの入力として読み取り**、各行を `decide.sh` に
流して結果を照合する。`*`（ワイルドカード）の列には複数の値を流し込んで同一結果を確認する。

**Rationale**: FR-017 は「手順記述と判定コードの両方を同期せよ」と要求するが、人手の規律だけ
では必ず乖離する。**文書をテストのフィクスチャにすれば、乖離がテスト失敗として現れる**。
これは憲章 V（変異で失敗するテスト）を満たす具体的な方法でもある。表の書式を固定するのは、
テストがパースするため。

**Alternatives considered**:
- 同期をドキュメントの注意書きに留める: 検出手段がなく、FR-017 が実効性を持たない
- 判断表をコード内にのみ持つ: FR-004 / FR-007 の人間向け説明がコードの読み解きになり、
  `references/criteria.md` の存在意義がなくなる
- 判断表を TSV など別ファイルにしてコードが読む: 真実源が 3 つ（表・コード・SKILL.md）に
  なる。表がコードの入力になると、表の破損が例外として現れず静かに誤動作する

## R-10. プラグイン名とバージョン（D-10）

**Decision**: プラグイン名 `placement-decision-flow`、スキル名 `placement-decision-flow`
（ディレクトリ名と一致）、バージョン `1.0.0`。

**Rationale**: Agent Plugins §5.5 の命名制約（1〜64 文字、`a-z` `0-9` `-` `.`、先頭と末尾は
英数字、`--` と `..` を含まない）を満たす。Agent Skills 仕様は `name` が**親ディレクトリ名と
一致する**ことを要求するため、プラグイン名とスキル名を揃える。記事の図
（`placement-decision-flow.svg`）と用語が一致し、由来が追える。初回リリースのため
憲章 VI に従い `1.0.0`。

**Alternatives considered**:
- `skill-or-agent` / `skill-vs-agent`: 判断の内容（配置先）よりも 2 択を強調してしまい、
  実際には 3 層 + 手順/コードの区別があることを表せない
- `placement-advisor`: 短いが、判断の対象（配置）が何の配置かが曖昧
- `agent-placement-flow`: 記事の図と用語がずれ、由来が追いにくい

## R-11. 出力言語（D-11）

**Decision**: **スクリプトの出力は ASCII の識別子**（`result=decision` など）。
**AI が利用者へ提示する文面は日本語**。`SKILL.md` の `description` は憲章 II に従い
`Use when:` を含む英語トリガーを併記する。

**Rationale**: 機械可読な出力を ASCII に固定すると、テストの期待値がロケールに依存せず、
比較も単純になる。人間向けの説明は利用者の言語（日本語）で行う。憲章 II が `description` に
英語のトリガーを要求するのは、スキルの発見が説明文の一致度で行われるため。

**Alternatives considered**:
- 出力も日本語: テストの期待値がロケールや端末エンコーディングの影響を受けやすくなる
- 出力も英語で統一: 利用者向けの説明が英語になり、日本語での対話と混ざって読みにくい

## R-12. テストの実行形態（憲章 V）

**Decision**: `tests/run.sh` が `tests/test_*.sh` を**ディレクトリ探索で自動収集**して実行し、
成功・失敗件数を報告する。各テストは出荷コードを**直接実行して**駆動し、期待値はテスト内に
明示する。`helpers.sh` のような共有ヘルパは作らず、各テストは自己完結させる。

**Rationale**: 憲章 V は「テストをランナーの収集対象に配置する」ことを要求する。外部のテスト
フレームワークを持ち込むと依存が増える（憲章 VII）ため、探索と実行だけを行う最小のランナーを
自作する。**探索にすることで、テストファイルを追加したのに実行されない事故を防ぐ**。
共有ヘルパを作らないのは、ヘルパが実装のコピーになって変異を検出しない状態（憲章 V）を
避けるため。

**Alternatives considered**:
- bats / shunit2: 成熟しているが追加依存になる（憲章 VII）
- 固定リストのテストファイル: 追加漏れが静かに起きる。憲章 V の「収集対象」の趣旨に反する
- pytest で bash をサブプロセス実行: Python 依存が増え、憲章 VII に反する

---

## R-13. 判断表のワイルドカードと短絡の意味

**Decision**: 判断表の `*` は「そのフィールドを評価しない」を意味する。これは評価順序による
**短絡**を表す。テストは `*` の列に `yes` / `no` / `unknown` の 3 値を流し込み、
`target` が変わらないことを確認する。

**Rationale**: FR-021 の評価順序を表に反映するには、短絡を表現する記号が必要。`*` を素直に
「任意」と読めるため、利用者にもテストにも意図が伝わる。`unknown` を流し込むテストが
**評価順序の正しさを直接検証する**（先行ゲートで確定するなら、後続が未回答でも判断が返る）。

**Alternatives considered**:
- 全 81 通りを列挙: 表が巨大になり、人間が読んで判断基準を理解できなくなる（FR-007 に反する）
- 短絡を表に書かずコードのみで表現: 表とコードが乖離し、FR-017 の同期対象が曖昧になる
